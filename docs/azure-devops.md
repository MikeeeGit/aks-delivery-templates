# Azure DevOps consumers

Use a private Azure Repos application project and workload-identity service connections. Public Azure validation remains credential-free on hosted agents. Declare a repository resource named `aksTemplates`, pinned to the reviewed full template commit. See [build](../examples/azure-build.yml) and [deploy](../examples/azure-deploy.yml) callers; review the pinned implementation commit and replace the example project/service-connection names.

The build stage template takes `stageName`, `serviceConnection`, `deploymentEnvironment` (default `image-build`), `configFile`, and `pool`. It first checks project privacy and protected-branch metadata on a hosted agent, then schedules the approved build job. The `image-release-<stageName>` artifact records the source/digest pair. Deployment job output variables are also named `imageDigest` and `sourceCommit` on the `receipt` step; use the artifact when selecting an explicit later promotion.

The deploy stage template requires `stageName`, `serviceConnection`, `deploymentEnvironment`, `environment`, `region`, `clusterSlot`, `sourceCommit` and `imageDigest`; `configFile` and `pool` are optional. Stage names must be unique when invoking it for both slots. The render job checks the old source is an ancestor of the triggering branch, snapshots it, and requires the approval-environment parameter to match the target's `approval_environment` name. This shared field is the environment name on either host.

For the complete current-build path use [build-deploy.yml](../azure-pipelines/stages/build-deploy.yml). Inputs are `buildServiceConnection`, `deployServiceConnection`, `environment`, `region`, `clusterSlots` (default `[aks01]`), `deploySequentially` (default true), and optional `configFile`, `buildPool`, `deployPool`, `buildEnvironment`, `stageName` (default `Application`). It builds once, passes the deployment job's `Build.receipt.sourceCommit`/`Build.receipt.imageDigest` outputs to each render stage, and preserves the producer dependency. Both slots consume that same digest. The build artifact is `image-release-Application_Build` with the default stage prefix.

For a previously successful build use [promote.yml](../azure-pipelines/stages/promote.yml). Specify numeric `buildRunId` and trusted `buildDefinitionId`, `buildArtifact`, deploy `serviceConnection`, environment/region and selected slots. Its default artifact `image-release-BuildApplication` matches the standalone build template; set `image-release-Application_Build` for the combined caller. The metadata-only hosted stage verifies the selected run succeeded in the same repository on the protected branch and that its receipt matches the run and commit. No rebuild occurs. Avoid mutable human build-number lookup: the numeric build ID is unambiguous. Retain release artifacts for your rollback period.

[deploy-selected.yml](../azure-pipelines/stages/deploy-selected.yml) is the lower-level wrapper for an already known source/digest pair. It accepts one or both `clusterSlots`, preserves their order when sequential, and uses approval environments `<environment>-<region>-<slot>`. Those names must match the target configuration. Explicit parallel mode starts both after selection/producer checks and has independent results. There is no automatic cross-slot rollback.

Create those environments in advance, with required approvers, branch restrictions and exclusive-lock checks. Restrict service connections and private pools to the intended pipelines. Do not grant open pipeline access. The environment-gated deployment downloads only the current run's named artifact and checks the independently passed receipt digest. It rechecks the protected branch before AzureCLI authentication and fails if the branch changed during approval. Set an appropriate pipeline retention policy for private artifacts.

AzureCLI@2 uses the selected workload-identity service connection and its isolated CLI configuration (the default `useGlobalConfig=false`). The helper checks actual tenant and target subscription, so a connection cannot silently select a different target. Give builds scoped ACR push rights; give deployment identities Cluster User and namespace-scoped AKS RBAC Writer. Run the separate [bootstrap stage](bootstrap.md) with its own privileged connection and approval environments before first application delivery.

The private agent needs Linux amd64, Python 3.10+, Azure CLI, private API DNS/routing, and outbound access for verified tools/dependencies. Builds additionally need Docker/Buildx and registry access. `System.AccessToken` is passed only to read-only project/branch/build/artifact API helpers. Grant project/repository/build read permissions; never print or forward it into application manifests. Configure branch build-validation policies separately; `pr: none` does not create an Azure Repos branch policy.

The independent controller/common-service tier uses [platform-services.yml](../azure-pipelines/stages/platform-services.yml), a dedicated privileged service connection and `platform-<environment>-<region>-<slot>` approvals. It preserves selected-slot sequential/parallel control, hosted receipt preparation and same-run artifact binding. See [platform lifecycle](platform-services.md) and its [inactive caller](../examples/azure-platform.yml). Bootstrap does not replace this Helm/platform stage.
