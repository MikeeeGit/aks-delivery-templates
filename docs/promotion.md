# Promotion, rollback and traffic cutover

Build a reviewed application commit once. Record its image digest/source commit from the successful build receipt. Use the same pair for both slots and later environments when compatible. Never rebuild just to assign a new environment tag. Environment differences live in committed Kustomize overlays and reviewed external secret references.

The selected-build promotion workflow reads an explicit successful build run ID and its retained receipt. A build always uses its triggering protected-branch commit; promotion can select that older committed release, provided it remains an ancestor of the current protected branch. Configure one/both slots and sequential mode explicitly. A failed first slot stops sequential promotion before the second; parallel promotion has independent outcomes. Per-slot approvals remain in effect.

Deploy to the candidate slot first. Verify rollout, actual frontend IP, health/readiness, configuration, workload identity, external dependencies and representative requests. The maintained Envoy profile owns candidate addresses `10.81.0.21` and `10.81.4.21`; the optional direct-Service and retired NGINX profiles use `.20`/`4.20`. Do not let two controllers/Services claim the same IP. Only live Service/Azure checks establish actual allocation. See [controller migration](ingress-migration.md).

Built-in verification checks `/readyz` and exact slot/source revision over selected-cluster port-forwards. The maintained profile also requires current-generation Gateway and every declared HTTPRoute listener status, then validates HTTPS through Envoy with the real Host/SNI and trusted certificate. It cannot accidentally test whichever cluster the active Application Gateway serves. Keep separate post-cutover checks for the actual Application Gateway frontend Host/path/TLS route. Failure stops the job and sequential progression; it never performs an unreviewed `rollout undo` or routing change.

Promotion requires a retained receipt from a successful producer and a passed [immutable-image security gate](image-security.md). Missing legacy scan receipts fail closed; use a newly reviewed build rather than editing a receipt to bypass that policy. The scanner report is a separate private artifact, not part of the single-file release artifact.

Application Gateway/DNS configuration has a separate state, approval and release path. Change its active backend only after candidate probes and application tests pass. Review Host headers, paths, ports, TLS trust, timeouts and connection draining. Application deployment does not imply or perform traffic cutover.

Keep the previous slot healthy through the observation/rollback period. Reverting gateway routing restores the previous traffic target. Reverting an application release means explicitly selecting the previous successful source/digest pair, rendering it again for the target and obtaining a new deployment approval. The framework does not use blind `rollout undo`, and it cannot reverse database/data migrations. Plan data compatibility and recovery separately.

Deployments serialize per selected GitHub target; Azure environments require exclusive locks. Apply is not transactional. A dry-run succeeds before the actual apply, but admission/network failures can still leave partial changes. Inspect the state after failure and repeat a reviewed operation. Removed manifest objects are not pruned automatically; deletion and namespace retirement are explicit operator work.

ConfigMap changes are declarative. Applications that need a restart must encode a pod-template change or configuration checksum in source; the helper does not conceal an unconditional restart. A maintenance page is another reviewed application/traffic configuration, not an automatic cluster-wide switch.
