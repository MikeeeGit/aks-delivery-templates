# Delivery design and compatibility

The system separates Terraform infrastructure, independently versioned cluster services and application delivery. It selects environment, region and one or both target clusters. Current-build and selected-build promotion reuse an immutable release; sequential cluster deployment is the default.

| Template lineage | Public implementation and qualification |
|---|---|
| `kustomize-deploy-template.yaml` | Retained pattern: [delivery.py](../scripts/delivery.py), [GitHub deployment](../.github/workflows/deploy-selected.yml), [Azure deployment](../azure-pipelines/stages/deploy-selected.yml). Committed overlays, explicit clusters, digest injection, render/review/apply/rollout. |
| `update-config-map-template.yaml` | Reviewed declarative [ConfigMap](../examples/configmap.yaml) and local Kustomize generators replace runtime private-file substitution. |
| `create-app-secret-provider-template.yaml` | [CSI resource](../examples/secret-provider-class.yaml), exact namespaced API support, and concrete demo ServiceAccount/CSI mounts. Infrastructure federation/vault grants are explicit prerequisites. |
| `create-cert-secret-provider-template.yaml` | [Certificate resource](../examples/certificate-provider-class.yaml) plus the demo's implemented CSI TLS synchronization and Gateway API HTTPS profile. Real vault object/certificate provisioning is operator-owned; no embedded secret material. |
| `set-maintenance-mode-template.yaml` | Automatic maintenance switching remains deferred. Explicit reviewed app/traffic releases and [cutover/rollback](promotion.md) preserve a controllable path; no claim of equivalent automatic maintenance automation. |
| `run-postman-tests-template.yaml` | [verify_service.py](../scripts/verify_service.py) replaces external collection fetching with selected-cluster readiness/revision checks and current Gateway/HTTPRoute status plus verified HTTPS Host/SNI. The sample adds smoke tests. Business-specific collections are not reproduced. |
| `initial-services-deploy-template.yaml` | [platform_services.py](../scripts/platform_services.py), [GitHub platform](../.github/workflows/platform-services.yml), [Azure platform](../azure-pipelines/stages/platform-services.yml) preserve separate Helm releases, namespace sets, workload identities, common manifests and diagnostics. Optional monitoring fits the engine; corporate agents/tokens and telemetry integration are not implemented defaults. |

The NGINX compatibility profile retains the reviewed source chart/version, namespace/class, per-cluster private frontend, replicas/autoscaling and resource settings. It tightens trust/source ranges, replaces uninstall-before-install with reviewed upgrades and is explicitly retired. Envoy/Gateway API is a deliberate migration, not a renamed NGINX installation or an assertion of annotation-level equivalence. [Migration](ingress-migration.md) records forwarded-header trust, session affinity, timeout, buffering and application-test differences. The direct-Service demo remains an optional simplified path; it is not the original full platform tier.

Targeted fixes include Entra user credentials instead of administrator kubeconfigs; explicit tenant/subscription and cluster maps; isolated credentials; no source-overlay mutation; no ignored failures; public credential-free CI; approved private deployments; independent artifact checksums; scoped privileges; TLS validation; and explicit rollback/cutover. Platform packages/CRDs/values/runtime images are pinned and reviewed. Existing namespace security labels survive reruns, and CRD ownership conflicts are surfaced rather than force-overwritten.

Builds use an immutable pushed digest and the mandatory [HIGH/CRITICAL image-security gate](image-security.md) before emitting a promotable receipt. Successful producer/run/source bindings and scan receipt fields are checked during selected-build promotion. A digest identifies bytes; the receipt binds a reviewed source/digest pair and is not a cryptographic source attestation. Manual low-level digest/source deployment remains an explicit operator path. Mutable deployment tags, secret Docker build arguments, disabled TLS verification and automatic unreviewed rollout undo are not carried forward.

Source-specific .NET/business builds, database deployment, registry replication, commercial monitoring credentials, alternate out-of-hours approval environments and automatic maintenance are not generic defaults. They require reviewed extensions. Examples and tests cover the implemented delivery contracts. No live Azure deployment, preview authorization enforcement or external cutover is inferred from offline tests.
