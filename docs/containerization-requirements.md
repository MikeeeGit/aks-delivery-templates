# Containerization requirements and implementation coverage

This document maps the [containerization platform plan](containerization-platform-plan.md) to maintained public code. It distinguishes implementation, optional integrations, missing capabilities and runtime evidence. Review date: **21 September 2026**.

The runnable baseline preserves three separate delivery tiers, private dual AKS, managed identities and federations, Key Vault CSI, Helm, Kustomize, Azure CNI Overlay with Cilium, Application Gateway WAF and a separately reviewed traffic switch. Envoy Gateway/Gateway API replaces community ingress-nginx. Argo CD is an additional deployment method.

**The complete design is broader than the runnable baseline.** Linkerd/mesh PKI, Windows workloads, scheduled jobs, a multi-service business application, enterprise observability and regional recovery are not established by a successful baseline run. **Dynatrace is excluded from the current worked deployment**; its design remains an optional extension, not a trial prerequisite.

## Status and evidence

| Status | Meaning |
| --- | --- |
| Implemented | Maintained code implements the capability. This alone does not prove a live Azure deployment. |
| Optional | Maintained inputs/code need explicit selection and external prerequisites. |
| Example only | A reference profile or procedure exists; wider workload behavior is not supplied. |
| Not implemented | No completed maintained integration was found. Documentation or a generic extension point is insufficient. |
| Runtime unproven | Corresponding real-environment acceptance has not been recorded. Rendering or kind cannot substitute for it. |
| Replaced | An explicit modernization changes a mechanism while retaining the responsibility. |

Phases and appendices refer to the sanitized plan. The underlying design dates from 2025 and incorporates its later Cilium revision. Historical completion statements and prices are context, not current public release evidence. This matrix contains no private tenant, endpoint, credential or deployment inventory.

## Corrections that affect implementation

These are compatibility and safety corrections to the earlier design, not additional claims of completed integration.

- **Cilium is a concrete platform choice.** Its AKS implementation is Linux-only, `ipBlock` does not select pod/node addresses, and host-network pods have different enforcement boundaries. Extra ACNS capabilities are not implied by choosing Cilium. Review the selected AKS/Cilium version and test the actual traffic paths. [Microsoft Cilium documentation](https://learn.microsoft.com/en-us/azure/aks/azure-cni-powered-by-cilium).
- **System-pool sizing must follow current AKS constraints.** Do not carry older burstable/2-vCPU system-pool suggestions into a deployment. The worked profile documents explicit lab sizing; validate system-pool requirements, regional SKU availability, quota and upgrade surge before planning. [Microsoft system-pool guidance](https://learn.microsoft.com/en-us/azure/aks/use-system-pools).
- **Authentication and authorization are separate.** An Entra Free tenant does not by itself establish that Azure RBAC for Kubernetes is unavailable. Select Azure RBAC or native Kubernetes RBAC deliberately, grant the required authority and verify real identity access. [Microsoft authorization documentation](https://learn.microsoft.com/en-us/azure/aks/entra-id-authorization).
- **NetworkPolicy allows are additive.** An unrestricted egress rule is not an Internet-only exception. Namespace and pod selectors have different combinations; DNS needs the protocols and targets used by the cluster. Temporary diagnostics must not leave a permanent broad allow rule. [Kubernetes NetworkPolicy documentation](https://kubernetes.io/docs/concepts/services-networking/network-policies/).
- **Mesh certificate automation needs an explicit lifecycle.** `Certificate` and `Issuer` objects are instances of installed CRDs, not themselves CRDs. Automatic issuer renewal does not remove trust-anchor rotation, overlap, restart and recovery work. Use the selected Linkerd version's actual values and supported cert-manager/trust-manager procedure. [Linkerd certificate rotation](https://linkerd.io/docs/tasks/automatically-rotating-control-plane-tls-credentials/).
- **Retired mesh alternatives are historical context.** Upstream Open Service Mesh is retired; it should not be presented as an equal current adoption recommendation. [Microsoft OSM notice](https://learn.microsoft.com/en-us/azure/aks/open-service-mesh-about).
- **Optional monitoring credentials need a current contract.** A historical tenant-level token assumption does not establish the right credential model for a new Dynatrace deployment. Consult the current per-cluster setup and privilege requirements, keep credentials outside Git/state and test their rotation. This extension remains excluded from the worked trial. [Dynatrace Kubernetes setup](https://docs.dynatrace.com/docs/ingest-from/setup-on-k8s/deployment/full-stack-observability).
- **HTTPS ingress is not end-to-end workload mTLS.** The sample terminates its ingress TLS at Envoy and serves backend application HTTP. Service-mesh encryption, stateful recovery and zero-downtime claims each require their own implementation and evidence.

## Acceptance needed to change a status

Attach commit/tool versions, selected targets, run identifiers and redacted test results to the release evidence. Keep private endpoint inventory, credentials, kubeconfigs, plans/state and secret-bearing outputs outside public repositories.

| Capability | Evidence required |
| --- | --- |
| Core real-Azure three-tier deployment | Actual Terraform outputs; successful federated CI login; selected-cluster platform and application authorization with negative tests; real CSI access; per-slot application image/readiness; HTTPS through WAF; selected-slot switch and rollback while observing responses. |
| Multi-service and scheduled applications | Independent release receipts; dependency and schema compatibility; required traffic allow/deny cases; Job/CronJob ownership, scheduling, concurrency, idempotency, completion/failure and cleanup behavior. |
| Optional Linkerd/PKI | Supported pinned components and CRDs; actual Cilium/security-profile compatibility; successful injection; mTLS/authorization positive and negative checks; issuer/root rotation, failure and recovery procedure. |
| Optional Dynatrace | Supported per-cluster credential/profile setup; least-required privileges and egress; actual workload/node telemetry and alerts; credential rotation and removal. **Excluded from the current worked deployment.** |
| Cilium policy | Real allowed and denied paths on the selected AKS network profile, including DNS and any required external dependency; diagnostic evidence from the enforcing engine. |
| Capacity and regional recovery | Measured load and HPA behavior; node disruption and upgrade headroom; recoverable state/data/credentials; an exercised regional plan with measured RTO/RPO. |
| Full removal and reconstruction | Explicitly authorized ordered Kubernetes/cloud cleanup; cloud load-balancer cleanup before network removal; state and cleanup authority retained until dependencies are gone; expected soft-deleted resources recorded; a separate reconstruction run. |

Update implementation status and runtime evidence separately. Code can close a missing capability; only its corresponding environment-specific acceptance closes the proof gap.
