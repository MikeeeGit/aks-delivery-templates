# GitHub Actions consumers

Use private application repositories. Public CI stays on hosted workers without Azure trust. Copy the [build caller](../examples/github-build.yml) and [deploy caller](../examples/github-deploy.yml) into the private repository's `.github/workflows/`. The examples pin an immutable implementation commit. When upgrading, update both the reusable workflow reference and template-ref to the same reviewed full commit SHA. Do not rely on mutable branches for delivery templates.

Create an `image-build` environment and one named environment per target (`pprd-uks-aks01`, `pprd-uks-aks02`). Configure allowed protected branches, required reviewers, no self-review/bypass where available, and restricted runner access. Review the account plan's support for private-repository environment approvals before enabling apply. YAML does not create these protections.

Create the separate bootstrap environments and identity described in [bootstrap](bootstrap.md), then invoke `bootstrap.yml` before the first application deployment. The workflow checks privacy on a hosted worker before scheduling a privileged private job. Do not reuse the bootstrap identity for build or ordinary deployment.

Create separate `platform-pprd-uks-aks01`/`platform-pprd-uks-aks02` environments for the independently versioned Helm tier. [platform-services.yml](../.github/workflows/platform-services.yml) accepts explicit slots/sequential selection and a dedicated privileged `client-id`; [platform setup](platform-services.md) and its [caller](../examples/github-platform.yml) describe the contract. Namespace bootstrap alone does not install the ingress/platform tier.

For Azure OIDC trust use the **private caller repository** and its actual subject configuration. New GitHub.com repositories created after July 15, 2026, and repositories renamed/transferred after that date, use immutable subjects such as `repo:OWNER@OWNER_ID/PRIVATE_APP@REPO_ID:environment:ENVIRONMENT_NAME`. Older repositories may retain `repo:OWNER/PRIVATE_APP:environment:ENVIRONMENT_NAME`; custom subject templates can differ again. Inspect the caller's OIDC settings and match the exact subject, rather than assuming the legacy form. See [immutable subjects](https://docs.github.com/en/actions/reference/security/oidc#immutable-subject-claims).

The issuer is `https://token.actions.githubusercontent.com`, audience `api://AzureADTokenExchange`. Build and deployment identities should differ. Build needs scoped ACR push rights appropriate to registry RBAC/ABAC mode; deploy needs AKS Cluster User plus namespace-scoped AKS RBAC Writer. No client secrets are needed. See [Azure Login OIDC](https://github.com/Azure/login#login-with-openid-connect-oidc-recommended).

Call `build.yml` with `template-ref`, `client-id`, optional `config`, `build-environment`, and JSON `runs-on` labels. Outputs are `image-digest` and `source-commit`; the private `image-release-<run-id>` artifact records the pair. A temporary Docker configuration isolates the ACR login token, and an ephemeral digest-pinned BuildKit builder is removed after building. Azure login uses a job-specific CLI configuration directory with action post-cleanup.

Call `deploy.yml` with `template-ref`, `source-commit`, `image-digest`, `environment`, `region`, `cluster-slot`, `client-id`, optional `config`, and private-worker `runs-on` labels. Select the digest/source pair from the successful build receipt. Source must be an ancestor of the triggering protected branch. The hosted render job has no Azure authentication. It uploads an immutable same-run artifact and passes a separate receipt checksum to the environment-gated job. After approval, the protected branch is rechecked before login; a changed branch requires a fresh run.

For both slots call `deploy-selected.yml` with the same inputs except `cluster-slots` JSON replaces `cluster-slot`. Choose `["aks01"]`, `["aks02"]` or both, in the required order. `deploy-sequentially` defaults true; the second job depends on the first successful rollout and verification. False uses parallel jobs, each with its own environment gate. A build→deploy caller passes the build reusable workflow's outputs directly into this wrapper.

For later release selection call `promote.yml` with `build-run-id` and the trusted **caller** `build-workflow` filename (default `image-build.yml`), plus the same target-selection/authentication inputs. Grant the caller `actions: read` as well as `contents: read` and `id-token: write`. A hosted job reads exactly `image-release-<run-id>` from a completed successful manual protected-branch run in this same private repository. It verifies producer workflow, repository, run ID, artifact digest when supplied by GitHub, and source commit before forwarding the receipt pair. The selected build can be older; deployment still requires its source to be an ancestor of today's protected branch. Expired/deleted artifacts fail closed; retain build receipts for the intended rollback period. No new image is built during promotion.

Use ephemeral workers with the `aks-private` label and private API reachability. The default hosted build worker can only reach public ACR endpoints; change its labels for a private registry. Client installation supports Linux amd64. Callers need `contents: read` and `id-token: write`; the guarded jobs narrow permissions. All action versions are full commit pins from official upstream repositories.

GitHub concurrency serializes one target without cancelling an active deployment. Multiple named application pipelines using the same namespace must also share an operational serialization rule. A caller can deliberately promote an older build; the framework does not silently pick the newest run or rebuild for the other slot.
