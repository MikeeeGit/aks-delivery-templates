# Archived ingress-controller compatibility profile

This opt-in profile preserves the reviewed archive's ingress-nginx chart **4.12.1**, namespace `ingress`, release `nginx-ingress`, class `nginx`, HTTP/HTTPS ports, internal load balancer per cluster, Local traffic policy, two replicas, autoscaling 2–5 at CPU60, resource limits and worker settings. The controller is retired; this profile is a migration/compatibility reference, not a currently supported controller recommendation. It is excluded from the default demonstration config. `allow_retired_ingress_nginx: true` explicitly acknowledges the choice in each target. Evaluate current advisories and a supported replacement before a new production deployment. No alternative controller is silently selected.

Copy this directory's contents into a separate private platform repository only after choosing the compatibility path. Set actual tenant, subscription, cluster names, namespace workload-identity client IDs and reviewed network ranges. The configuration selects an exact official chart URL, version and package SHA256. `values/aks01.yaml` and `aks02.yaml` use controller-owned `10.81.0.20` / `10.81.4.20` frontends and the corresponding AKS subnet. Both use gateway `10.81.8.0/24` as their source/trusted forwarded-header range instead of the source's unrestricted proxy trust. Review any additional health-probe or operational source ranges in your environment.

The controller frontend and the direct-Service application's frontend **cannot own the same IP simultaneously**. Follow the application's explicit ingress-profile migration: the app Service becomes ClusterIP and Ingress objects route to it. This platform chart owns the ingress controller; the application owns its Deployment/ClusterIP Service/Ingress and CSI certificate references. Gateway probe, Host/path and backend TLS settings belong to the separately managed gateway layer. Do not remove the old frontend before the alternate path and rollback plan are ready.

Namespaces, explicit workload ServiceAccounts and the reviewed common ConfigMap are applied by the platform engine. ServiceAccount annotations reference managed identities created by Terraform; their federated subjects must match namespace/name on each cluster. The engine does not create those Azure identities or grant Key Vault access. No secret payloads, corporate agents or credentials are included. Configure additional common manifests only after review; CRD lifecycle remains separate.

The archive also installed Dynatrace Operator1.5.1 optionally, then a per-cluster DynaKube object. That commercial monitoring integration needs operator-managed CRDs, a reviewed supported operator version, tenant endpoint, credentials and policy. Use the engine's additional pinned releases and common manifests after those prerequisites exist; the compatibility profile does not fabricate working credentials or install an unconfigured commercial agent.

See the [platform guide](../../docs/platform-services.md) for private approvals, chart review, diagnostics and upgrade/rollback boundaries.
