# Maintained private Gateway API profile

Copy this directory's contents into a trusted private platform repository. This profile pins Envoy Gateway **v1.9.1**, Gateway API **v1.6.1**, chart package/OCI digest, both CRD bundles and controller/data-plane/certificate/shutdown runtime images. Recheck the [official compatibility matrix](https://gateway.envoyproxy.io/news/releases/matrix/) on every upgrade; the reviewed 1.9 line covers Kubernetes 1.33–1.36. See the [shared lifecycle contract](../../docs/platform-services.md) and [migration guide](../../docs/ingress-migration.md).

The controller runs in `envoy-gateway-system`, watches `platform-demo`, and uses [GatewayNamespace mode](https://gateway.envoyproxy.io/docs/tasks/operations/gateway-namespace-mode/). `GatewayClass/envoy-gateway` and `Gateway/platform-demo-private` are platform-owned. Per-cluster `EnvoyProxy/private-proxy` creates a private LoadBalancer Service with explicit subnet, gateway-subnet source range, Local traffic policy, two replicas, HPA 2–5 and pinned images. It binds candidate addresses `10.81.0.21` and `10.81.4.21`; verify actual allocation before traffic cutover. Old `.20` frontends can coexist while migrating.

The two HTTPS listeners, `https-web` and `https-api`, use `platform-demo-tls` in the same namespace. The application supplies matching HTTPRoute parent references, CSI TLS synchronization and an ordinary ClusterIP Service. Its workload ServiceAccount uses the same dedicated applied UAMI in both clusters, with federation per issuer. Replace the synthetic client ID in platform and app source together. Bootstrap restricted namespace settings and conditional application [custom-resource permissions](../authorization/README.md) before delivery.

`ClientTrafficPolicy` trusts **one** forwarded hop only for the private, source-restricted Application Gateway path. Changing proxy topology changes that trust calculation. No global request-body buffering is enabled. NGINX cookie affinity, buffering, idle timeouts, rewrites and other annotations require application-specific migration tests; HTTPRoute timeouts are not a blanket translation.

Common manifests are applied after CRDs/controller readiness. At first installation the Gateway may remain unprogrammed until the application CSI mount synchronizes the real TLS Secret. App delivery then waits for current Gateway/HTTPRoute conditions and verifies both hosts through the selected Envoy Service with valid TLS Host/SNI and exact cluster/revision. The temporary port-forward selects the candidate cluster; separate Application Gateway tests qualify the actual frontend path.

Node egress must allow the pinned runtime registry and CSI vault, or use reviewed ACR mirrors. Use the [firewall platform example](https://github.com/MikeeeGit/azure-firewall/blob/main/examples/aks-platform/README.md). Gateway API/Envoy CRDs are explicit reviewed upgrades; `crds.enabled=false` and `--skip-crds` prevent implicit chart lifecycle changes. The optional rate-limit service is disabled; its upstream default image is not part of the deployed workload and must be pinned before enabling that feature. These files are synthetic and no live Azure deployment is claimed.
